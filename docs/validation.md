## 关键回归

- 请求体：64 KiB 边界、超限、声明长度、无声明长度和流式读取；分别验证管理错误及 OAuth 错误结构，正常授权仍可完成。
- UserInfo：获取令牌后修改当前资料，原授权的姓名、头像及来源保持原认证快照；缺失资料不回退到当前用户；保留 `profile` scope 和逐字段请求条件；两个认证事件的并发请求互不串扰。库处理器、直接公开地址和兼容别名均覆盖。
- 管理员：仅由实际回调的稳定数字 ID 匹配显式配置，空值、非法值与其他身份均不授予管理员权限。
- Cookie：旧配置的 HTTPS 回归先失败，修复后通过。检查实际 Connect 回调响应及认证库全部 Cookie 的名称和属性；主 Cookie 为 `__Host-liteauth.session`，具有 Secure、HttpOnly、SameSite=Lax、Path=/，没有 Domain。旧名称即使携带有效签名值也不被接受。
- 部署：隔离环境、管理员配置、资源占位值、路由、额外预览入口、自动请求日志以及 staging 前端产物哈希检查。
- 页脚：版本、仓库链接、颜色、键盘焦点、320px 换行、路由错误和 404；刷新、导航及改变浏览器时钟均不改变构建时间。非 Lite 入口保持白色次要按钮，Lite 入口保持绿色。

## 已部署环境验证

staging 和 production 均使用被忽略的独立配置发布 API 与 Web。生产执行了 dry-run，随后使用 `--skip-build` 提升 staging 已验证的同一份前端产物。远端迁移列表没有待执行迁移。

两个环境的 `scripts/verify-deployment.mjs` 均通过七组公开冒烟：SPA 深链接与安全响应头、保留路由返回 JSON、匿名会话和管理权限、Discovery／JWKS、用户信息认证要求、不支持的授权类型以及关闭动态注册。管理与 OAuth 超限请求返回对应的 HTTP 413。

对两个环境的实际页面另用全新 Chromium 上下文验证桌面和 320px 移动端：登录页、404、路由参数错误页均显示唯一页脚；仓库链接、浅灰色、按钮配色、键盘操作、构建时间稳定性及无横向溢出均通过。

两个环境实际提供的 JavaScript／CSS 资源与本地 staging 清单的 SHA-256 相同；HTML 的应用入口与资源引用相同。Cloudflare 会向 HTML 注入动态挑战脚本，因此不将最终 HTML 响应的逐字节哈希作为产物一致性断言。

staging 使用临时、隔离、非管理员 D1 身份及签名会话完成四组真实 HTTP 协议交互：两种 `login_method` 分别请求 `openid profile` 和普通 `profile`。验证授权、同意、PKCE 兑换、ID Token 签名、issuer／audience／nonce、UserInfo 快照及兼容地址。测试后已删除临时身份及其会话、应用、授权、令牌和记录。

**这组 staging 协议检查的身份来自合成会话，没有重新执行 Linux.do 上游人工登录。** 本地 Connect 回归使用模拟上游响应；公开冒烟也不能替代真人登录。之前版本的真实双通道登录证据归档保留，本轮不将其写成新的实测。

## 审查与已知限制

独立安全审查及架构审查覆盖了请求体限制、授权快照、Cookie 安全属性和部署边界。发现的部署期间产物变更窗口已增加上传前后哈希检查；部署时仍要求单进程，不同时重建产物。该结果不表示所有可能的漏洞都已排除。

- 管理站 Cookie 名称变化后，已有用户需要重新登录。已经签发的下游令牌不因本次改名被撤销。
- New API 联调继续延期。
- 用户真实改名的人工测试按维护者指示跳过；稳定 Linux.do ID、凭据归属、撤销版本和管理员追溯具有自动回归覆盖。
- GitHub Private vulnerability reporting 尚未确认启用，必须在仓库公开前核验。此次没有推送或公开远端。
- 本次未进行生产数据恢复、回滚或加密主密钥轮换演练，也不以已写好的运维文档作为演练证据。
